# Личный кабинет

Перенос PHP-CMS (`CMS l2`) в Nuxt. Кабинет работает с теми же таблицами MySQL, что и старая CMS,
поэтому миграция данных не нужна, а старые пароли подходят: мастер-аккаунты — bcrypt,
игровые аккаунты — `base64(whirlpool)`, как ждёт логин-сервер.

## Страницы

| Путь                        | Было                     | Что делает                                                    |
|-----------------------------|--------------------------|---------------------------------------------------------------|
| `/login`, `/register`       | login.php, register.php  | вход и регистрация мастер-аккаунта; `?ref=КОД` — приглашение   |
| `/cabinet`                  | index.php, game_account.php, transfer.php | баланс, игровые аккаунты, персонажи, перевод монет, смена паролей |
| `/cabinet/donate`           | donate.php, payment_status.php | счёт на оплату (карты, СБП, ЕРИП), QR, статус, история |
| `/cabinet/referrals`        | referral.php             | реферальная ссылка, приглашённые, награды                     |
| `/admin`                    | admin.php                | уникальные заходы, подтверждение платежей, начисление/списание, журнал |
| `/admin/referrals`          | admin_referral.php       | настройки и предметы реферальных наград, ручная проверка      |
| `/forum`                    | —                        | форум сервера; читается без входа, пишется мастер-аккаунтом. Подробности — [FORUM.md](FORUM.md) |

Английские версии: `/en/...`. Тексты кабинета — `cabinet` в `app/locales/ru.ts` и `en.ts`, форума — `forum`.

## Устройство

```
shared/cabinet.ts            настройки (ID монеты, курс, лимиты, серверы), типы API — общие для сервера и фронта
shared/visits.ts             разделы заходов и московские сутки
shared/forum.ts              разделы, лимиты и типы форума
server/utils/                db (пулы MySQL), auth (сессия), passwords, payments, referrals, characters, rate-limit, forum/
server/api/auth/*            вход, регистрация, выход, текущий пользователь
server/api/cabinet/*         обзор кабинета, создание игрового аккаунта, смена пароля, перевод монет
server/api/payments/*        счета на оплату
server/api/referrals/*       реферальная страница и проверка наград
server/api/admin/*           админ-панель
server/api/visits.post.ts    уникальный заход по IP (сайт, статистика, кабинет, форум)
server/api/forum/*           чтение и запись форума
server/tasks/referrals/      проверка реферальных наград каждые 10 минут (было cron_referrals.php)
server/middleware/csrf.ts    изменяющие запросы к API — только со своего сайта
server/database/install.sql  схема таблиц для новой установки (кабинет, форум, заходы)
server/database/forum.sql    только таблицы форума — для уже работающей базы
server/database/visits.sql   таблица заходов — для уже работающей базы
app/plugins/visits.client.ts учёт захода при открытии страницы
app/pages/{login,register}.vue, app/pages/cabinet/*, app/pages/admin/*, app/pages/forum/*
app/layouts/cabinet.vue, app/components/cabinet/*, app/assets/css/cabinet.css
app/components/forum/*, app/assets/css/forum.css
```

- **Сессия** — зашифрованная httpOnly-cookie `azimut_session` (ключ `NUXT_SESSION_PASSWORD`), 30 дней.
- **Админы** — логины из `NUXT_ADMIN_LOGINS` (через запятую), раньше было зашито `admin`.
- **Ошибки API** возвращаются кодом (`data.code`), текст для игрока берётся из `cabinet.errors` в locales, у форума — из `forum.errors`.
- **Настройки** без секретов (ID монеты 4037, курс, мин./макс. сумма, срок счёта, список игровых серверов) —
  в `shared/cabinet.ts`. Доступы к БД — только в переменных окружения.

## Заходы

Первая таблица на `/admin` — уникальные IP по разделам. Колонки: сегодня, 7 суток, 30 суток (включая сегодня) и всё время. Сутки — календарный день Москвы.

| Раздел | Страницы |
|--------|----------|
| Сайт | `/` |
| Статистика | `/stats` |
| Личный кабинет | `/cabinet` и вложенные, `/login`, `/register` |
| Форум | `/forum` |

Английские адреса `/en/...` попадают в тот же раздел. Админка (`/admin`) не считается. Один IP в одном разделе — одна строка за сутки. «Всего» — разные IP по всем разделам, а не сумма строк: человек на сайте и на форуме стоит в двух строках и один раз в итоге.

Заход записывает браузер при открытии страницы (`POST /api/visits`). Повтор в том же разделе в те же сутки не создаёт строку: у `site_visits` первичный ключ `(day, section, ip)`.

Новая установка создаёт таблицу из [`server/database/install.sql`](../server/database/install.sql). На уже работающей базе скрипт можно запускать повторно:

```bash
mysql -u cms_register -p la2 < server/database/visits.sql
```

## Что изменилось по сравнению с PHP-версией

Поведение то же, но исправлены места, где можно было потерять или задвоить монеты:

- Списание при переводе персонажу и при ручном списании — одним запросом `coins = coins - N WHERE coins >= N`.
  Раньше параллельные запросы могли увести баланс в минус.
- Реферальная награда сначала записывается в `referral_claims` (уникальный ключ), потом выдаётся.
  Раньше при двух одновременных проверках предметы могли выдаться дважды.
- При сбое выдачи предмета в игру монеты возвращаются, а в `donate_log` пишется `transfer_refund`.
- HWID и IP для защиты от твинков в реферальной программе собираются по каждой таблице отдельно.
  В PHP-версии ошибка запроса к `la2x.accounts` (на которую нет прав) обрывала сбор, и HWID фактически
  не проверялся. Теперь проверка HWID работает, как задумывалось.
- Ограничение частоты: вход (10 попыток на логин и 20 на IP за 15 минут), регистрация (5 в час с IP),
  создание счетов и игровых аккаунтов.
- Смена пароля игрового аккаунта в кабинете (в PHP-версии её не было): пароль хранится как
  `base64(whirlpool)`, как ждёт логин-сервер. Обязателен текущий пароль — e-mail при регистрации
  не подтверждается, поэтому одной сессии мастер-аккаунта для доступа к чужому аккаунту недостаточно.
  Не более 10 попыток в час на мастер-аккаунт.
- Тексты ошибок БД больше не показываются игрокам (в PHP был включён `DEBUG_DB_ERRORS`), только пишутся в лог.
- Реферальные награды проверяются при входе в кабинет (не чаще раза в минуту на игрока) и задачей каждые 10 минут;
  раньше — при каждой загрузке страницы кабинета и по cron.
- Счёт на оплату: 4 способа — Visa/Mastercard, Visa/Mastercard/Мир, СБП и ЕРИП (в BYN).
  QR генерируется на сервере (без стороннего api.qrserver.com); для СБП он ведёт на ссылку
  из `NUXT_SBP_PAYMENT_URL` (по умолчанию — `runtimeConfig.sbpPaymentUrl` в `nuxt.config.ts`).
  На телефоне рядом с QR есть кнопка «Оплатить в приложении банка» с той же ссылкой.
  Подключение платёжного шлюза, callback и курс BYN — в [PAYMENTS.md](PAYMENTS.md).

## Переход со старой CMS

1. Подготовить сервер, задать переменные окружения и открыть MySQL для IP сайта
   ([DEPLOY.md → «Свой сервер»](DEPLOY.md#свой-сервер-ubuntu), шаги 1–3).
2. Задеплоить (на сервер деплой идёт по умолчанию, см. DEPLOY.md, шаг 4).
   CI сам проверит, что кабинет видит базу (`/api/health`). Старая CMS может работать параллельно — данные общие.
3. Проверить вход старым мастер-аккаунтом, список персонажей, создание счёта и его подтверждение в `/admin`.
4. Перенаправить старые адреса на новые (например, в nginx старого хостинга:
   `login.php` → `/login`, `register.php?ref=…` → `/register?ref=…`, `index.php` → `/cabinet`),
   чтобы не потерялись уже разосланные реферальные ссылки.
5. Отключить старую CMS, удалить её файлы с хостинга и **сменить пароль `cms_register`**:
   он хранился открытым текстом в `config.php`.

## Локальная разработка

Кабинет и форум работают с той же схемой MySQL, что и боевой логин-сервер. Локально её поднимает MariaDB в Docker: база `la2` (кабинет, форум, игровые аккаунты) и `la2x3` (заглушки персонажей, `items_delayed` и статистики).

```bash
npm run db:up           # первый запуск создаёт таблицы и демо-данные
cp .env.example .env    # NUXT_DB_HOST=127.0.0.1, NUXT_DB_PORT=3307, пользователь и пароль azimut
npm run dev
```

Демо-вход: мастер-аккаунт `admin` / `azimut` (админ, 1000 монет), игровой аккаунт `player` / `azimut`, персонаж Azimut, одна тема на форуме. Сбросить базу: `npm run db:reset`.

Без `NUXT_SESSION_PASSWORD` в dev-режиме используется временный ключ; в production без него лендинг работает,
а запросы кабинета падают с ошибкой (при старте в лог пишется предупреждение).
Проверка реферальных наград вручную: `/admin/referrals` → «Проверить и выдать награды».
